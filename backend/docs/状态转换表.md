异常中的 `/confirm` 仅接受该异常已由宠主批准的当前版本，不执行普通 pending_confirm 预留规则；`/resolve decision=resume` 在重要变更时暂不写 resolved_at，最终帮手确认后统一结案，批准动作记录在 TaskEvent。预算批准前不得继续购买，缺货替换必须得到宠主确认；已完成清单内容不改，复制到新版本并保留 completed 状态及旧证据引用关系（按稳定 item_key 追溯），服务端核验须读取同一预约各版本证据，新增记录只允许当前版本，不能伪造旧版本记录。

超时任务由后续后端定时扫描并在确认、接单、开始请求时惰性检查，统一使用数据库时间，持锁后重新校验，确认与超时竞争只能一个成功；提醒作为 TaskEvent 交由前端读取，本轮不实现通知发送。服务超时以 scheduled_end 为界，同一超时事件只触发一次，进入异常后不能靠反复恢复消除超时，恢复执行须批准合理新结束时间并重新检查冲突。

重要修改在 in_service/pending_verify 禁止直接 PATCH，必须走异常；异常变更时间也必须重新检查窗口、可用时间和冲突，无法满足则保持 exception 待双方安排。第一轮暂不设计帮手强行终止进行中的服务，帮手可报告异常，宠主确认后续；双方无响应保留 exception，不自动判定完成。

服务类型核验：home_visit 核验逐项照料记录；dog_walking 必须为 dog，核验 pickup/departure/return 及时间顺序；errand_buy 核验 purchase 凭证、实际合计不超过批准预算及 delivery，费用均 decimal(10,2)，不调用支付系统。任何核验不能以照片存在自动认定照料正确。

事务共同要求：锁需求、预约及必要帮手档案后重读版本和状态，领域更新与 TaskEvent 一并提交；verify、submit、confirm 和 records 的幂等遵循 API 清单，不以客户端禁用按钮替代服务端幂等。
